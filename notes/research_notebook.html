2026-07-11 · notes

Two meanings of OOD Historical — still the project's terminology

Decision. “ID/OOD” is ambiguous here and must always be qualified:

  • pretraining-ID/OOD — relative to what Chronos-2 saw during pretraining. A pretraining dataset is not one giant series: it is a family of related series, and training examples are windows from individual series.
  • probe-ID/OOD — relative to what the linear probe was trained on. Training a probe on electricity and testing it on pedestrian counts is probe-OOD even though both are pretraining-ID.

Every dataset used to date is pretraining-ID (provenance: data/chronos2_seen_manifest.md). The later “OOD transfer” experiments are therefore probe-OOD only — the project has never yet tested a pretraining-OOD dataset. Open question: univariate vs multivariate / covariates (still unprobed).

2026-07-14 · notes + commits 655605d…c89392f

Shared forecast-slot probe, series bootstrap, capacity ablation Historical

The busiest day of the project — three additions, all run on GPU the same week (old numbering: 12 layers, L11 last).

1 · Shared forecast-token probe — structural alignment with the native head

Chronos-2's own head does not read a pooled vector: for H = 64 it reads 4 forecast-slot hidden states (one per 16-step output patch) and applies the same head weights to each. The pooled probe is shape-compatible with that head but semantically mismatched. The new probe mirrors the native layout linearly: one shared Linear(768, 21·16) applied to each of the K = 4 slot states, patches concatenated to the 64-step forecast. It has ~4× fewer parameters than the pooled probe (258,384 vs 1,033,536 at q21). The two probes answer different questions:

  • Pooled: can the whole future trajectory be decoded from one global summary vector?
  • Shared-slot: can each layer's forecast-slot states be decoded by the same kind of shared linear readout the native model uses?

Because encoder attention is non-causal, adding forecast slots changes all token states — so controlled pooled variants (content_K, reg_K) were re-run on the same K-slot pass.

2 · Series-level cluster bootstrap

Plain language: with one test set you cannot rerun the world, so the bootstrap fabricates ~5000 artificial test sets by resampling the real one and reads the middle 95 % of the metric's spread. But test windows overlap within a series (stride 64 ≪ span 576), so resampling individual windows would pretend there is more independent evidence than exists and give too-narrow intervals. The unit of resampling is therefore the whole series: draw S series with replacement, keep all their windows. One shared resampling matrix per dataset makes every layer-vs-L11 difference paired.

3 · Probe-capacity ablation (q1/q9/q21)

Worry: the 21-quantile head has ~1.03 M parameters — maybe the mid-layer advantage is a big-probe artifact. The head was shrunk to deciles (q9, 442,944 params) and median-only (q1, 49,216). Cross-set comparisons must use the per-quantile mean pinball loss (loss / 2Q); raw summed losses are incomparable across Q.

2026-07-29 · notes (Jul 28 section) + commit c4ec967 + SLURM logs 66617320, 66639567

Capacity-control heads: does the pattern survive a stronger decoder? Verified result

Why a stronger decoder changes the question. A linear probe measures linear decodability. If a layer looks bad linearly, the information may still be there, just not linearly arranged. Swapping in a higher-capacity head re-asks the question as “does the intermediate-layer advantage survive increased decoder capacity?” — explicitly not a replacement for the linear result.

The change. Two from-scratch heads, structural clones of the native ResidualBlock (Linear→ReLU→Dropout→Linear + linear skip, no LayerNorm, hidden = native d_ff = 3072, dropout 0), trained with the identical protocol as the linear probe (fixed 300 epochs — early stopping was considered and deliberately rejected to keep the comparison clean):

  • content_mlp_head — head on the pooled content vector; 4,575,360 params at q9 (10.3× the pooled linear probe). Isolates “replace the linear map with a nonlinear one”.
  • forecast_slot_native_head — ONE shared head over the K = 4 forecast slots; 2,915,616 params at q9 (26.3× the shared linear probe). The architecture-faithful analogue of the native head — but trained from scratch; it is not the pretrained native head.

The driver additionally records both a target-test oracle best layer (diagnostic) and a source-validation selected layer (the deployable, fair choice) — the first appearance of this distinction in the project.

Run and result (all 3 sources × both families, 3×3, q9, GPU July 29; results/extended_v1/ood_transfer/capacity/): under the pooled content readout the mid-layer advantage survives the 10× nonlinear head (8/9 cells Δ>0 with CI excluding zero; same single null, Uber→KDD). Under the shared forecast-slot head the advantage largely disappears: oracle best layers sit late (L8–L12), five cells have Δ exactly 0 (best = L12), and source-validation selects L11/L12 in every cell. The pilot's PENDING checklist in PLAN.md (electricity first, then the rest) was overtaken — everything ran and was committed.

M4 Hourly — why it needs a different split

One probing window needs C + H = 512 + 64 = 576 consecutive points. A within-series temporal split needs a training span and a disjoint test span from the same series — at least 2 × 576 = 1,152 points. Both M4 nulls in the 4×4 are M4-as-source. For a stronger paper version, the notes record two options: cross-series splitting for every dataset, or replacing M4 with a long hourly dataset. MASE — two definitions; never use the bare word

mase_context (implemented, reported everywhere Verified implementation): per-window denominator d = mean_t |x_t − x_{t−24}| over that window's own 512-step context (488 lagged pairs), clamped at 1e-8 with the clamp count recorded (0 in current runs). Numerator: mean absolute error of the raw-unit median forecast over the 64-step horizon. Aggregation: plain mean over windows (window-weighted). No test observation enters the denominator (the context precedes the forecast origin). This is the definition behind every reported MASE number — including the columns literally named mase in the OOD CSVs and native_mase in summaries; the bootstrap artifacts name it explicitly (mase_context keys, definition string embedded in the npz metadata).

Not robust under transfer

Because the aggregation is a plain mean of ratios, individual cells can be governed by a single window and are unsafe to read at face value across datasets. Two failure modes, both seen in the M4 transfer cells (Jul 31 entry): (1) the raw-unit inverse μ + σ·sinh(z) amplifies any out-of-range probe median exponentially, so one cross-dataset extrapolation can push a cell's mase to 10⁵–10⁶ while its quantile_loss (arcsinh space) stays ~4; (2) near-constant / near-zero target windows give a denominator ≈ 10⁻⁵, so a good forecast still scores MASE in the thousands. Prefer the median (or a trimmed mean) per-window MASE for cross-dataset summaries; the mean is reliable only within a single well-scaled dataset. Point estimates named mase in the OOD CSVs inherit this and should not be quoted as means.

mase_train_series (canonical train-series MASE Implemented, not run — denominator only): one denominator per original series from its raw training-portion history (m = 24), same value for all of that series' test windows, NaN-and-exclude policy for invalid cases, undefined (NaN) under the cross-series split. The denominator ships in build_windows (test_denominator, with n_denominator_invalid counted), but no metric, result, or figure uses it — experiments/run_id_forecasting.py states this explicitly. The full metric remains Planned; no mase_train_series numbers exist anywhere in results/.
